# Recommendations: WLDD Creator's Network

Based on the workflow observed in `research.md` (Campaign → Post link → Screenshot approval → Insights approval → Invoice → Payment/GST). Keeping this short and focused on the highest-impact gaps rather than a long feature wishlist.

## 1. Automate proof-of-post instead of manual screenshots
"Pending Screenshots" sat at 2.5K — nearly equal to total links added, meaning verification is the biggest bottleneck. Pulling post/insights data directly via Instagram's official API (where the page grants access) instead of relying on manually uploaded screenshots would collapse the approval backlog and remove a whole manual review step.

## 2. Status timeline on each post/invoice
Right now a post just shows a single current status ("Approved Post"). Add a simple visible timeline (Submitted → Screenshot Reviewed → Insights Approved → Invoiced → Paid) with timestamps, so creators know exactly where something is stuck without opening a support ticket.

## 3. Bulk actions on "My Works"
With thousands of links per account, doing anything one row at a time doesn't scale. Add multi-select + bulk submit / bulk "generate invoice for all approved-uninvoiced links" — directly addresses the "Uninvoiced Links: 625" number sitting there unresolved.

## 4. Payment ETA / aging visibility
Invoices show status labels but no due date or aging (e.g. "overdue by 12 days"). Adding an expected payment date and a simple aging indicator on the Invoices page would let creators (and finance) spot late payments proactively instead of chasing manually.

## 5. In-app notifications tied to actual state changes
The only proactive nudge seen was a generic banner about WhatsApp verification. Real-time notifications for the events that matter — screenshot rejected, insights approved, invoice paid — would reduce the need to keep re-checking the dashboard.

## 6. Rate card versioning / negotiated overrides
Rate cards are shown per page and format, but campaigns clearly vary in price (₹12,500 flat vs. custom brand deals). Letting a campaign override the base rate card explicitly (with a visible "custom rate" tag) would make pricing discrepancies self-explanatory instead of relying on tribal knowledge.

## Not recommended right now
Avoid adding unrelated modules (e.g. content scheduling, DM inbox, analytics dashboards beyond what's needed for invoicing) — the platform's value is in being a tight ops layer for the approval→invoice pipeline; scope creep there would dilute it rather than improve it.

## Tech stack — revised per constraints

Notes only, nothing implemented yet.

- **Auth:** No OTP. User enters phone number + password only. Password is **auto-generated by the system** (not user-chosen) and delivered to the user (e.g. shown once on signup / sent via WhatsApp or SMS) — need to decide the delivery channel and whether a forced "change password" flow exists later. Hash with bcrypt, sessions via JWT (access + refresh), no Redis for session storage — refresh tokens can live in the DB (Postgres) instead if revocation is needed.
- **Background jobs:** No Redis/BullMQ. Given the scale seen (thousands of links, not millions), a simpler approach works: `node-cron` for scheduled tasks (e.g. periodic Instagram re-scrapes) running in the same Node process, or a lightweight DB-polling job table if jobs need to survive restarts/retries.
- **Screenshot/asset storage:** Cloudinary (signed direct-upload, image transforms/CDN delivery built in) instead of S3.
- **Instagram data:** No official Graph API/OAuth integration — use an **Apify actor** to scrape public Instagram data instead. This matches recommendation #1 (replacing manual screenshots) but via scraping rather than API access.
- **Payments:** No Razorpay/payment gateway integration. Payment status is recorded manually by an admin/finance user marking an invoice as paid — no live payment processing in-app.

### Reference: apify-instagram provider pattern (from wizwebitsolutions/affiliate-creator-tool)

Cloned and reviewed `https://github.com/wizwebitsolutions/affiliate-creator-tool.git` (`server/src/lib/providers/apify-instagram.js`) to understand their Apify-based scraping approach. Key points worth carrying over:

- Uses the official `apify-client` SDK, driven by an `APIFY_TOKEN` env var — no custom scraping code, all scraping logic runs inside Apify's actors.
- **Two separate actors** for two separate needs:
  - `apify~instagram-scraper` (profile scraping) — must be called with `directUrls: ["https://www.instagram.com/<username>/"]`, **not** `usernames: [...]` (the latter silently returns 0 results — a real gotcha worth avoiding from day one).
  - `data-slayer/instagram-post-details` (single post/reel scraping) — called with `postUrls: [<permalink>]`, one call per post/link, matching the "per-link" model this project also uses.
- Treats a missing/errored item as a distinct `PostNotFoundError` (dead/deleted/private link) vs. other thrown errors (auth/quota/network) — worth replicating so a broken creator-submitted link doesn't get confused with a transient scrape failure.
- Engagement fields default to `-1` ("unknown") rather than `0` when Apify returns null, to avoid falsely showing "engagement dropped to zero" — a good pattern to reuse for likes/comments/saves/shares on our own post-metrics table.
- Their overall stack (for reference, not necessarily to copy wholesale): Node.js/Express (plain JS, ESM) + Prisma + PostgreSQL on the server, Vite + React + TypeScript + Tailwind on the client, pnpm workspaces monorepo, Cloudinary for media, Playwright present (likely for auxiliary scraping/screenshotting), Sentry for error tracking. This lines up closely with the direction already recommended here (Postgres + Prisma, React frontend), reinforcing it rather than changing it.
